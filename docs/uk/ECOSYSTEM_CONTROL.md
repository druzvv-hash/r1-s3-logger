# R3: спільний час і керування приладами

Вимога власника від 09.09.2026, доповнення плану 1.11.
[Технічний контракт R3](https://github.com/druzvv-hash/lily-logger-r3/blob/main/docs/ECOSYSTEM_CONTROL.md) ·
[Часові шкали та обмеження](../ECOSYSTEM_TIME_SYNC.md) ·
[План R1-S3](R1_S3_PLAN.md).

**Це погоджена цільова поведінка. Зараз прошивка S1 передає маяки через BLE,
але ще не зберігає прив’язку між ввімкненнями, не коригує RTC від R3 і не
виконує групові START/STOP.**

## Час після ввімкнення

R3 має найкращий RTC у цій системі за вибором власника і є головним джерелом
часу. R1-S3 та інші сумісні прилади звіряються з ним. Так поєднуємо повільні
процеси напруги/струму, швидкі датчики R3 та події CAN в одному досліді.

| Ситуація | Як має працювати |
|---|---|
| Перше додавання приладу | Один раз явно прив’язуємо до свого R3 і дозволяємо віддалене керування. |
| Наступне ввімкнення | Сам знаходить довірений R3, автентифікується, отримує свіжий час і звіряє власний RTC. |
| R3 ще не ввімкнений або поза радіусом | Працює від власного RTC, показує відсутність джерела та повторює підключення. |
| R3 з’явився пізніше | Підключається й звіряє час; якщо йде запис, корекція чекає. |
| Уже йде запуск, запис або закриття файлу | RTC не змінюється. Після закриття беремо новий часовий знімок і лише тоді коригуємо RTC. |
| Час R3 недостовірний | Не переносимо його на інші прилади; показуємо причину. |
| BLE обірвався | Поточний запис продовжується. Після відновлення перевіряємо джерело, час і справжній стан запису. |
| Прив’язку видалено | Потрібне нове явне додавання; випадковий сусідній R3 не стає довіреним. |

Саме підключення **не запускає запис**. RTC й EEPROM не переписуються від
кожного маяка. Ключі зв’язку зберігаються окремо в NVS, не у файлах вимірювань
і не як збережений PIN. Часові мітки відліків та інтегрування енергії лишаються
на власному монотонному часі; уже записані дані не пересуваємо.

Звірений календарний час ще не означає точного збігу відліків між приладами.
Похибку та дрейф перевіряємо окремо; сам вибір R3 джерелом не доводить
мілісекундної точності. CAN потребує перевірки його власного адаптера.

Перед E2 також перевіряємо опис точності у файлах: зараз CSV для чинного RTC
зазначає похибку 1,1 с. Після звіряння від R3 ця межа повинна мати підтвердження;
інакше спочатку додаємо сумісне позначення невідомої/грубої точності. Не можна
ввімкнути корекцію й залишити у нових файлах необґрунтовану цифру.

## Головна панель R3

На R3 — список приладів із галочками, назвою, станом зв’язку, часу, пам’яті
та поточної сесії. Власний записувач R3 також можна додати окремим рядком.
Поточний BLE-сервер підтримує до трьох клієнтів; панель має показувати це
обмеження. Вибір R3 головною панеллю не потребує зміни наявних BLE-ролей.

1. Позначаємо потрібні підключені прилади. R3 перевіряє готовність усіх
   вибраних. Якщо хоча б один не готовий, груповий START не надсилається.
2. Натискаємо START. Кожен прилад підтверджує власну сесію та фактичний
   початок запису. Частковий успіх можливий при збої вже після перевірки;
   панель показує його окремо, не заявляє, що почали всі.
3. STOP стосується конкретних вибраних сесій. Прилад спочатку завершує
   запис буферів, закриває файл і лише тоді підтверджує успіх.

Показуємо окремо: **команду прийнято → запис триває → файл закривається →
файл закрито**, а також помилку або невідомий стан. Відсутність BLE не
означає «зупинено». Кнопка місцевого STOP зберігає пріоритет. Сесію, запущену
локально, можна зупинити з R3 лише за явного вибору саме цієї актуальної
сесії та дозволу приладу на віддалене керування.

Повтор START не створює другий файл. Запізнілий STOP не зупиняє нову сесію.
Після відновлення зв’язку R3 запитує фактичний стан; самовільного повторного
START або зупинки вже запущених приладів через частковий збій не буде.
Групова команда не гарантує фізично одночасного початку відліків.

## Порядок роботи й перевірки

| Етап | Результат |
|---|---|
| E1 | Збережена прив’язка, повторне підключення після ввімкнення R1/R3 у різному порядку, видалення довіри. |
| E2 | Звіряння RTC у спокої; перевірки недостовірного часу, пізнього підключення й відкладеної корекції після закриття файлу. |
| E3 | Команди з ідентифікаторами приладу/запуску/сесії; повтори, запізнення, швидкий START/STOP, місцеві дії та втрати BLE. |
| E4 | Список вибраних приладів і керування з R3; чесні результати для кожного, зокрема частковий успіх. |
| E5 | Явна версія файлів із групою досліду, джерелом часу та потрібними доказами; сумісність читачів. |

Перед E3 усуваємо знайдені в коді випадки: R1 зараз не приймає STOP у стані
STARTING; у R3 кінцевий обробник STOP потребує перевірки відповідності сесії,
а панель — відокремлення помилки від успішного закриття файлу.

Під час усіх тестів перевіряємо незмінність вимірів, FIFO у PSRAM, блокового
запису та цілісності файлів. Точне зіставлення часових шкал — окрема робота
S2. Файловий етап E5 узгоджується з S3, без двох несумісних розширень формату.
