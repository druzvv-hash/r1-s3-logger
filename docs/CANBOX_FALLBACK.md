# R1-S3 → CANBox: резервний маршрут, 2026-09-15

## Стан

Експериментальні прошивки: CANBox `0.3.0-dev`, R1 `0.27-canbox-dev`.
**Фізичне резервне START/STOP через BLE пройдено.** R1 відновлено через
прямий USB COM9 після обриву UART-запису; перевірено весь відновлений образ,
потім прошито й перевірено наявний профіль `esp32-s3-usb` для прямої консолі.

Підтверджено спарювання з PIN, ENROLL, SAVE, два цикли запису, повторний STOP,
продовження запису при BLE OFF, STOP після повторного підключення до тієї
самої сесії. Прив’язка збереглася після окремих перезапусків R1 і CANBox;
підключення без нового PIN працює. Перевірки CBX CHECK обох файлів пройшли.
На шині не було кадрів: це перевірка керування та закриття порожнього файла.

R1: RTC TICK OK, ADC OK, I2C errors=0, EEPROM generation=4. **SD R1: FAIL**.
SD CANBox готова. Одночасний запис R1+CANBox не перевірено.
Перед успішним спарюванням CANBox потребував перезапуску після тайм-аутів;
причина не встановлена. Див. протокол `C:\Projects\GLL CANBox\docs\R1_NATIVE_USB_BENCH_2026-09-15.uk.md`.

## Що працює в коді

- Новий окремий GATT-сервіс CANBox; старий FFF0/TLV більше не рекламується.
- Secure Connections із PIN, MITM, 16-byte ключем і збереженими bonds.
  Legacy pairing вимкнено. Заповнення сховища не витісняє старі bonds.
- USB `BLE PAIR` відкриває прив’язку на 120 секунд. `BLE ENROLL` окремо
  дозволяє поточному автентифікованому R1 керувати CANBox. Прив’язка зберігається
  в NVS, відсутність/помилка NVS не спричиняє автоматичного стирання.
- BLE callback лише додає 96-byte ECO1 до черги. NORMAL owner перевіряє
  identity, boot, TTL, permission, connection generation, session та виконує SD.
- STOP повертає closed після дренування, END/CRC, fsync та close. Втрата BLE
  не зупиняє запис. Кеш 32 запитів захищає повтори, змінений пакет із тим самим
  request ID відхиляється. Локальний STOP скасовує стару чергу віддалених команд.
- Поруч із `.cbx` створюється `.eco` з повними 64-bit session/group,
  boot контролера і CANBox та роллю `r1-fallback`. Невалідний UTC позначено явно.
  Низькі 32 біти сесії відповідають імені файла; колізія не перезаписує дані.
- На R1 використовується один наявний BLE worker та одне з’єднання.
  Вибір CANBox призупиняє канал R3; `BLE ON` повертає збережений R3.
  Прив’язки й bonds зберігаються окремо. За замовчуванням після boot обирається R3.
- Панель містить окремі CAN START/STOP/QUERY, актуальність стану та очікування
  результату. Рядки 64-bit ID не округлюються JavaScript. PIN не зберігається.

## Підключення після прошивання R1

1. Зупинити записи. На CANBox: `BLE PAIR`; взяти шестизначний PIN із USB.
2. На R1 у вкладці BLE ввести CANBox `98:A3:16:F1:39:D6` і PIN.
3. На CANBox перевірити `BLE STATUS`: authenticated=1. Виконати `BLE ENROLL`.
4. На R1 натиснути «Зберегти прив’язку CANBox». Дочекатись свіжого стану.
5. Запустити CAN-запис; перевірити recording на R1 і COM11. Зупинити;
   перевірити closed, а на CANBox виконати CHECK.
6. Пізніше обирати «Вибрати збережений CANBox» без PIN.

Еквівалентні R1-команди у звичайній оболонці `BOOT REV BLE <argument>`:
`CAN CONNECT <MAC> <PIN>`, `CAN SAVE`, `CAN ON`, `CAN START`, `CAN STOP`,
`CAN QUERY`, `CAN FORGET`. Через USB-панель:
`PANEL <id> DO <boot> <revision> BLE CAN START`; boot/revision брати з STATE.
CANBox: `BLE STATUS`, `BLE PAIR`, `BLE ENROLL`, `BLE FORGET`.
Для повторного спарювання після втрати bond спершу явно забути прив’язку
на обох пристроях; автоматичної підміни довіри немає.

## Контракт direct-control v1

UUID-префікси `7e57c100`, `7e57c101`, `7e57c102`, `7e57c103` мають спільний
суфікс `-7a1e-4e54-a930-64e137711031`:

| Префікс | Призначення |
|---|---|
| c100 | Primary service |
| c101 | ECO1 command/hello, Write With Response, authenticated |
| c102 | ECO1 status/result, authenticated Read; R1 опитує кожні 500 мс |
| c103 | 16-byte descriptor, Read; довіра все одно перевіряється через SMP |

Descriptor: `43425831010302020300000000000000`: CBX1, версія 1,
роль CAN-вузла 3, два канали, формат файла 2, capabilities 0x03
(passive CAN capture + direct START/STOP), чотири резервні нулі.
MTU не менше 99. Наявний ECO1 codec R3/R1 не змінений.
Час очікування результату на R1 — 12 секунд; невідомий результат не є STOP.
QUERY повертає фактичний стан після відхиленої команди. Команди не
пересилаються автоматично після втрати зв’язку.

## Межі готовності

Це перший direct-control адаптер, **не завершена інтеграція екосистеми**.

- Upstream CANBox → R3 ще не реалізований. `r3_available` у політиці поки
  не отримує runtime-сигнал; резервний режим обирає оператор явно.
  Автоматичне виявлення R3, пріоритет і передача сесії ще не кваліфіковані.
- R1 та CANBox запускаються окремо; групового одночасного старту немає.
  R1 не стає джерелом UTC. Точного вирівнювання CAN/INA ще немає.
- Після reboot R1 його новий boot не може зупинити стару віддалену сесію;
  доступне локальне STOP на CANBox. Автоматичного перехоплення немає.
- `.eco` є початковим provenance sidecar, а не доказом завершеного запису:
  при помилці відкриття/живлення може залишитися orphan. Перевіряти `.cbx` CRC/END.
  Повного snapshot конфігурації, checksum sidecar і Reader/Viewer-інтеграції немає.
- Програмне відключення BLE та reboot/reconnect перевірено. Слабкий сигнал,
  повторне спарювання після втрати ключів, відмова SD під час запису,
  одночасний запис R1+CANBox та тривале навантаження ще не перевірені.
- GPIO4 CAN_TRACT_TEST — стендовий режим, owner direct-control працює в NORMAL.

## Перевірки

Збірки обох прошивок проходять. CANBox: тести формату й справжнього owner
із підставними радіо/SD межами (replay/conflict/wrong session/boot/identity,
expired, disconnect, local STOP, storage error). R1: 83 host-тести пройдено.
Окремий браузерний тест `tests/canbox_ui.cjs` перевіряє pending/recording/closed,
stale, незбережений peer, 64-bit ID та нерозголошення PIN.
Ці тести не замінюють двоплатний стенд.

Фінальний CANBox-стенд: `7fb7796a.cbx`, 7264 байти, 300 кадрів,
100 standard / 100 extended / 100 RTR, 0 drops. Вивантажена на ПК копія
пройшла незалежний `tools/cbx.py` CRC/END. Фінальні артефакти CANBox:
`docs/evidence/control-2026-09-15/firmware.json`, `pc-file.json`,
`canbox-control-final-bench.log`. Нові докази керування R1 збережено поруч
у `r1-canbox-native-*.json`; деталі — у протоколі прямого USB/BLE стенду.

## Уточнення власника після стенду

SD R1 була фізично вийнята: зафіксований SD FAIL очікуваний і не доводить
несправності карти чи інтерфейсу. Перевірка після встановлення карти ще потрібна.
Надалі R1 прошиваємо та підключаємо через прямий USB Serial/JTAG, COM9 на цьому ПК.

## Панель стану 0.28-canbox-dev

CANBox видно над усіма вкладками. Великий заголовок розрізняє запис,
закритий файл, відсутність готовності, непідключений пристрій, застарілий
або невідомий стан. Поруч є підключення збереженої нюхалки без PIN,
START, STOP, оновлення стану та перехід до прив’язки.

Немає зв’язку не означає «живлення вимкнено» або «запис зупинено».
Панель показує поточний запис лише за свіжим підтвердженням CANBox і
живим з’єднанням браузер → R1. Під час команди показує попередній
підтверджений стан та очікування результату. Готовність — це ознака
Ready від CANBox, не окрема діагностика SD чи доказ наявності CAN-кадрів.
Нові поля JSON `ready` та `authorized` не змінюють ECO1 на радіоканалі.

Перевірено браузером: старт/стоп, очікування результату, втрата BLE,
втрата зв’язку браузер → R1, заборона старту без готовності/дозволу,
збережена прив’язка, відображення 64-bit session та відсутність PIN у DOM.
Переглянуто мобільний макет 390 px. Після підключення плат 0.28 встановлено через COM9, hash перевірено.
Живий R1 підтвердив CANBox connected/fresh/ready/authorized=true, phase=idle.
SD R1 читається, generation=5, I2C errors=0. Запис під час цієї перевірки
не запускали. 83 host-тести пройшли.
